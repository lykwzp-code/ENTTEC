# EMU + ELM Portfolio Strategy

## Strategic proposition

**EMU discovers new creative language. ELM scales proven creative language into professional production.**

This is a hypothesis built from an observable public signal: ENTTEC states that ELM 2026 includes 130+ GPU shader effects ported from EMU.

That does **not** prove ENTTEC already uses this portfolio model internally. It simply shows that creative capability has already moved from one product to the other.

---

## 1. Keep the products distinct

### EMU
Primary mental model:

> “I’m a musician / DJ / producer. I want light to become part of my performance.”

Optimise for:
- expressive speed
- DAW / MIDI workflow
- low learning barrier
- experimentation
- music-first language
- individual creators / small teams

### ELM
Primary mental model:

> “I need to map and control a real spatial pixel system at professional scale.”

Optimise for:
- spatial control
- precision
- scale
- determinism
- integration
- professional live / touring / install workflows
- monitoring / commissioning / reliability

Do not turn ELM into “big EMU.”
Do not turn EMU into “small ELM.”

---

## 2. Proposed portfolio relationship

### Creator frontier
EMU:
- tests new creative interaction models
- works closely with artists
- tolerates controlled experimentation
- discovers useful visual primitives

### Production frontier
ELM:
- tests professional scale and reliability
- works with designers / integrators / touring teams
- turns selected creative capabilities into deterministic production tools

### Infrastructure frontier
S-PLAY and related hardware:
- unattended playback
- scheduling
- permanent deployment
- field execution

---

## 3. Feature graduation criteria

A feature should move from EMU learning into ELM consideration only if:

- more than one creator workflow validates the problem
- the concept remains useful when separated from a single artist’s style
- professional users can control it predictably
- output can be reproduced
- performance can scale
- it complements rather than disrupts ELM workflow
- Engineering can support it without creating unacceptable technical debt

Possible outcomes:

1. stays EMU-only
2. shared underlying engine, different UX
3. rebuilt in ELM
4. rejected entirely
5. becomes a separate service / workflow rather than a feature

---

## 4. Shared Creative Engine hypothesis

Possible shared internal modules:

- shader engine
- colour systems
- timing primitives
- beat / section analysis
- visual transition primitives
- artist-defined visual grammar
- AI-assisted translation
- media generation / transformation components

Benefits:
- less duplicated innovation
- consistent creative capability
- quicker experimentation in EMU
- cleaner professionalisation in ELM

Risk:
- architecture can become over-generalised and slow both products

Rule:

> Share primitives only when the engineering and UX benefits are real.

---

## 5. Portfolio research questions

- Which EMU workflows are musicians repeatedly using in ways the product team did not expect?
- Which EMU features are already relevant to professional ELM users?
- Which ELM capabilities are too complex for creators but could be surfaced through a simpler abstraction in EMU?
- Where are users currently moving between EMU, ELM and S-PLAY?
- Which use cases currently require third-party software, and why?
- Where is the creative handoff between musician, lighting designer and integrator most painful?

---

## 6. Portfolio KPI examples

- creator-to-professional feature graduation rate
- time from creator insight to validated experiment
- reuse of shared creative primitives
- reduction in duplicated implementation
- percentage of graduated capabilities adopted by ELM professionals
- cross-product user journeys
- revenue influenced by portfolio-level workflows
