# 07 — Product Specialist Operating Model

## Role mission

**Turn ambiguous user needs into validated product decisions across the ENTTEC ecosystem.**

The role is valuable when it closes the loop:

**user / creator  
→ problem definition  
→ hypothesis  
→ experiment  
→ product decision  
→ launch / adoption  
→ learning**

It should not be defined mainly as “support more products.”

---

## 1. Four responsibilities

### Discovery
- direct user research
- workflow observation
- separate requested features from underlying problems
- synthesize recurring friction

### Experimentation
- define smallest useful test
- prototype / workflow mock / pilot
- success / kill criteria
- learn before major roadmap investment

### Portfolio translation
- decide where a problem belongs
- distinguish EMU creator needs from ELM professional needs
- identify shared primitives only where justified

### Go-to-market learning
- use authentic creator work as education and evidence
- work with Marketing without becoming only a marketing role
- connect market response back into product learning

---

## 2. Eight role-health checks

### 1. Direct user access
Can the role talk to real users directly?

Strong:
- interviews
- user sessions
- customer visits
- beta groups

Weak:
- all feedback comes through Sales / Support

### 2. Independent problem space
Does the role own a persistent problem, not only tasks?

Strong:
> “You own creator onboarding / this workflow / this domain.”

Weak:
> “You help wherever needed.”

### 3. Experiment authority
Can the role turn a hypothesis into a real test?

Strong:
- pilot
- prototype
- user test
- limited beta

Weak:
- all ideas wait for roadmap approval

### 4. Engineering capacity
Can validated ideas receive actual implementation support?

Strong:
- named Engineering partner
- prototype / sprint capacity
- clear priority process

Weak:
> “Engineering is busy, but you can submit requests.”

### 5. Roadmap participation
Can the role bring evidence into prioritisation before decisions are final?

Strong:
- participate in trade-offs
- recommend scope / priority
- understand why things are rejected

Weak:
- roadmap is decided elsewhere
- Product Specialist only prepares launch / support material

### 6. Broader scope: ownership or support?
“Not limited to EMU” can mean:

Good:
- wider decision surface
- broader product responsibility

Bad:
- more products to support reactively

### 7. 12-month domain ownership
Can the role grow into an area where colleagues say:

> “This is Kai’s domain.”

Growth should increase:
- domain ownership
- decision rights
- product judgement
- outcome accountability

### 8. Discovery-to-outcome continuity
Can the role stay involved through:

**discovery → build → launch → adoption → iteration**

This is where product judgement compounds.

---

## 3. Four fundamentals

The eight checks reduce to:

**Access** — Can I learn from real users?  
**Ownership** — Can I focus on a problem?  
**Resources** — Can I act?  
**Decision & accountability** — Can I influence priorities and learn from outcomes?

---

## 4. What the role should not become

Avoid:

- reactive support for every SKU
- demo-only sales enablement
- product-information relay
- backlog secretary
- content role with no product authority
- pseudo-PM accountability without resources

Broader scope is useful only if it means broader **ownership**, not only broader **support load**.

---

## 5. Decision framework

Core question:

> **Which user problem deserves product investment, and where in the portfolio should it live?**

Evaluate:

- user pain
- frequency
- evidence quality
- strategic fit
- creator value
- professional value
- differentiation
- implementation cost
- support cost
- cross-product leverage

Do not prioritise only because:
- a famous artist asks
- a comment gets many likes
- one customer is loud
- it contains AI
- it looks good in marketing

---

## 6. Personal fit

The value proposition is not:

> “I am already a lighting expert.”

It is the combination of:

- technical / engineering background
- customer-facing experience
- requirements definition
- solution comparison
- UAT / acceptance criteria
- AI application work
- commercial exposure
- interest in physical-world creative experiences

Growth path:

> **Product Input → Product Decision Participation → clear domain ownership**

## 07 — Product Specialist Operating Model

### Role mission

这个岗位真正有价值时，应该闭合：

### Discovery
- direct user research
- 观察真实 workflow
- 把 feature request 与 underlying problem 分开
- 总结反复 friction

### Experimentation
- 定义最小 test
- prototype / workflow mock / pilot
- success / kill criteria
- 大投入前先学习

### Portfolio translation
- 判断问题应该落在哪个产品
- 区分 EMU creator need 与 ELM professional need
- 只有合理时才做 shared primitive

### Go-to-market learning
- 用真实 creator work 做教育和 evidence
- 和 Marketing 合作，但不退化成纯营销
- 把市场反馈重新带回 product learning

## 2. 八个岗位健康度检查

### 1. Direct user access
能不能直接接触真实用户？

强：
- interview
- user session
- customer visit
- beta group

弱：
- 所有反馈都靠 Sales / Support 转述

### 2. Independent problem space
有没有持续负责的问题，而不只是 task？

强：
> “你负责 creator onboarding / 这个 workflow / 这个 domain。”

弱：
> “哪里需要就帮哪里。”

### 3. Experiment authority
能不能把 hypothesis 真的做成 test？

强：
- pilot
- prototype
- user test
- limited beta

弱：
- 所有 idea 都要等正式 roadmap

### 4. Engineering capacity
已经验证的 idea 有没有实现资源？

强：
- 明确 Engineering partner
- prototype / sprint capacity
- 清晰 priority process

弱：
> “Engineering 很忙，但你可以提需求。”

### 5. Roadmap participation
能不能在决定前把 evidence 带进 prioritisation？

强：
- 参与 trade-off
- 推荐 scope / priority
- 知道为什么某些东西被拒绝

弱：
- roadmap 在别处决定
- Product Specialist 只做 launch / support material

### 6. Broader scope：ownership 还是 support？
“not limited to EMU” 可能是：

好的：
- 更大的 decision surface
- 更广 product responsibility

坏的：
- 更多产品需要 reactive support

### 7. 12 个月 domain ownership
能不能成长成别人会说：

> “这块是 Kai 负责。”

成长应该增加：
- domain ownership
- decision right
- product judgement
- outcome accountability

### 8. Discovery-to-outcome continuity
能否跟完整链路：

**discovery → build → launch → adoption → iteration**

这里才会真正积累 product judgement。

## 3. 四个核心维度

八个问题最终是：

**Access** — 能不能接触真实用户？  
**Ownership** — 有没有自己的问题空间？  
**Resources** — 能不能行动？  
**Decision & accountability** — 能不能参与优先级并从结果学习？

---

## 4. 这个岗位不应该变成什么

避免：

- 所有 SKU reactive support
- demo-only sales enablement
- product-information relay
- backlog secretary
- 没 product authority 的 content role
- 没资源却背 PM 结果的 pseudo-PM

Broader scope 只有意味着更大 **ownership** 时才有价值。

---

## 5. Decision framework

核心问题：

> **哪个用户问题值得产品投入，它应该落在 portfolio 的哪里？**

评估：

- user pain
- frequency
- evidence quality
- strategic fit
- creator value
- professional value
- differentiation
- implementation cost
- support cost
- cross-product leverage

不要只因为：
- 大牌艺人提出
- 评论点赞高
- 一个客户很强势
- idea 里有 AI
- 很适合 marketing

就直接优先。

价值不是：

> “我已经是 lighting expert。”

而是这些经历组合：

- technical / engineering background
- customer-facing experience
- requirements definition
- solution comparison
- UAT / acceptance criteria
- AI application work
- commercial exposure
- 对 physical-world creative experience 的兴趣

成长路径：

> **Product Input → Product Decision Participation → clear domain ownership**
