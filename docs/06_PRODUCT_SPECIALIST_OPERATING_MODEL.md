# 06 — Product Specialist Operating Model

## Role mission

**Turn ambiguous user needs into validated product decisions across the ENTTEC ecosystem.**

The role is valuable when it closes the loop between:

**user / creator  
→ problem definition  
→ hypothesis  
→ experiment  
→ product decision  
→ launch / adoption  
→ learning**

It should not be defined mainly as “support more products.”

---

## 1. Four responsibilities

### A. Discovery
- interview musicians, creators, designers, integrators and other users
- observe real workflows
- separate requested features from underlying problems
- synthesize recurring friction

### B. Experimentation
- define the smallest useful test
- write hypotheses and acceptance criteria
- use prototypes, workflow mocks or manual tests
- define success / kill criteria before scaling

### C. Portfolio translation
- decide where a problem belongs
- distinguish EMU experimentation from ELM professional requirements
- identify shared primitives only where justified
- maintain problem backlog separately from feature backlog

### D. Go-to-market learning
- turn authentic creator use into education and case studies
- use content as a product-learning surface
- work with Marketing without becoming only a content role

---

## 2. What healthy ownership looks like

A Product Specialist should be able to answer:

- What problem space do I own?
- Which decisions can I make?
- Which decisions do I influence?
- Who makes final roadmap calls?
- Which Engineering / Design / Marketing resources can I access?
- What happens when resources conflict?
- Can I stay involved from discovery through post-launch learning?

---

## 3. What the role should not become

Avoid:

- reactive support for every SKU
- demo-only sales enablement
- product-information relay
- backlog secretary
- marketing role with no product authority
- pseudo-PM accountability without resources or decision access

Broader scope is only valuable if it means broader **ownership**, not merely broader **support load**.

---

## 4. Decision framework

The core product question is not:

> “What feature should we add?”

It is:

> **“Which user problem deserves product investment, and where in the portfolio should it live?”**

Evaluate opportunities using:

- user pain
- frequency
- evidence quality
- strategic fit
- creator value
- professional value
- differentiation
- implementation cost
- support cost
- cross-product leverage

Do not prioritise solely because:
- a famous artist asks
- a comment gets many likes
- Sales has one loud customer
- the idea contains AI
- the feature would look good in marketing

---

## 5. Example operating loop

### Input
An Artist Lab creator says:

> “The second chorus should feel wider than the first, but EMU makes it easiest to repeat the same pattern.”

### Product Specialist
1. observes the workaround
2. checks whether other creators have the same problem
3. reframes it as “repeated-section variation”
4. tests a lightweight workflow
5. defines measurable success
6. works with Engineering if the hypothesis is validated
7. tests the result with creators
8. decides whether to ship, iterate or kill
9. later evaluates professional relevance for ELM

This is the bridge from **customer input** to **product decision participation**.

---

## 6. Personal fit for this role

The value proposition is not “I am already a lighting expert.”

It is the combination of:

- technical / engineering background
- customer-facing experience
- requirements definition
- solution comparison
- UAT / acceptance criteria
- AI application work
- commercial exposure
- strong interest in physical-world creative experiences

The intended growth path is:

> **Product Input → Product Decision Participation → clear domain ownership**

That is why the role is attractive only if ENTTEC can provide real access to users, product decisions and execution resources.

## 06 — Product Specialist Operating Model

### Role mission

**把模糊的用户需求转化成经过验证的产品决策。**

这个角色真正有价值时，它应该闭合下面这条链：

**user / creator  
→ problem definition  
→ hypothesis  
→ experiment  
→ product decision  
→ launch / adoption  
→ learning**

它不能主要被定义成“支持更多产品”。

---

## 1. 四项核心责任

### A. Discovery
- 访谈 musician、creator、designer、integrator 和其他用户
- 观察真实 workflow
- 把 feature request 和 underlying problem 分开
- 总结反复出现的 friction

### B. Experimentation
- 定义最小有用测试
- 写清 hypothesis 与 acceptance criteria
- 用 prototype、workflow mock、manual test 做验证
- 在扩大投入前定义 success / kill criteria

### C. Portfolio translation
- 判断问题应该落在哪个产品
- 区分 EMU 的创作者实验与 ELM 的专业生产要求
- 只有在合理时才寻找 shared primitive
- problem backlog 与 feature backlog 分开维护

### D. Go-to-market learning
- 把真实 creator use 转成教育内容和 case study
- 把 content 当成 product-learning surface
- 和 Marketing 合作，但不能退化成纯内容岗位

---

## 2. 健康 ownership 是什么样

Product Specialist 应该能回答：

- 我拥有哪个 problem space？
- 哪些决定我可以自己做？
- 哪些决定我可以 influence？
- 谁做最后 roadmap call？
- 我能使用哪些 Engineering / Design / Marketing resource？
- 资源冲突时谁做决定？
- 我能否从 discovery 一直跟到 post-launch learning？

---

## 3. 这个角色不应该变成什么

避免：

- 所有 SKU 的 reactive support
- demo-only sales enablement
- product information relay
- backlog secretary
- 没有 product authority 的 marketing role
- 没资源、没决策权却背 PM 结果的 pseudo-PM

Broader scope 只有在意味着更大的 **ownership** 时才有价值，而不是 support workload 变大。

---

## 4. Decision framework

核心问题不是：

> “下一个 feature 做什么？”

而是：

> **“哪个用户问题值得投入产品资源，它应该落在 portfolio 的哪里？”**

评估维度：

- user pain
- frequency
- evidence quality
- strategic fit
- creator value
- professional value
- differentiation
- implementation cost
- support cost
- cross-product leverage

不要只因为以下原因就优先：
- 大牌艺人提出
- 评论点赞高
- Sales 有一个很强势的客户
- idea 里面有 AI
- 很适合 marketing

---

## 5. 一个 operating loop 示例

### Input
Artist Lab 里的 creator 说：

> “第二次副歌应该比第一次更宽，但 EMU 最容易的做法还是重复同一个 pattern。”

### Product Specialist
1. 观察 workaround
2. 检查其他 creator 是否也遇到
3. 重构成“repeated-section variation”问题
4. 测试轻量 workflow
5. 定义 measurable success
6. 如果 hypothesis 被验证，再和 Engineering 推进
7. 再次让 creator 测试
8. 决定 ship / iterate / kill
9. 最后再判断是否对 ELM professional user 也有意义

这就是从 **customer input** 到 **product decision participation** 的桥梁。

---

## 6. 我为什么适合这种角色

价值不是：

> “我已经是 lighting expert。”

而是这些经历的组合：

- technical / engineering background
- customer-facing experience
- requirements definition
- solution comparison
- UAT / acceptance criteria
- AI application work
- commercial exposure
- 对 physical-world creative experience 的强兴趣

希望形成的成长路径：

> **Product Input → Product Decision Participation → clear domain ownership**

所以这个岗位只有在 ENTTEC 能提供真实用户接触、产品决策参与和执行资源时，才真正有吸引力。
